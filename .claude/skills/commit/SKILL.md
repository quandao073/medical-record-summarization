# Intelligent Commit Skill

Create precise, well-structured git commits with automatic change analysis, smart grouping, and bilingual message support (English/Vietnamese).

## Step 1: Gather Context

Run these in parallel:

```bash
git status
git diff --cached --stat
git diff --cached
git diff --stat
git log --oneline -10
git branch --show-current
```

For large staged diffs (>500 lines total), use `--stat` first, then selectively read key files with `git diff --cached -- <file>`.

## Step 2: Determine Mode & Language

### 2a: Check for changes

| Condition | Action |
|-----------|--------|
| No changes at all | Abort: "No changes to commit." |
| Merge conflict markers in status | Abort: "Resolve merge conflicts first." |

### 2b: Determine commit scope

| Situation | Action |
|-----------|--------|
| User passed `--all` flag | Batch mode, skip scope question |
| ONLY staged changes exist | Single mode, skip scope question |
| ONLY unstaged/untracked exist | Batch mode, skip scope question |
| BOTH staged AND unstaged exist | **Ask user** (see below) |

When both exist, ask:

> **"Both staged and unstaged changes detected. What would you like to commit?"**
> 1. "Only staged changes" → Single mode
> 2. "All changes" → Batch mode

### 2c: Ask language preference

After scope is determined, ask:

> **"Commit message language?"**
> 1. **EN** — English only
> 2. **VI** — Vietnamese body, English subject (Conventional Commits standard)

## Single Commit Mode

### Analyze Diff

Read `git diff --cached` output carefully. Skip binary file contents. For lock files (package-lock.json, yarn.lock, uv.lock, etc.), note their presence but do not base the message on their contents — group them with their manifest.

### Commit Message Format

```
type(scope): concise imperative description

- Body bullet 1
- Body bullet 2
```

### Type Selection

| Type | Use when |
|------|----------|
| `feat` | New functionality or capability |
| `fix` | Bug fix or error correction |
| `refactor` | Code restructuring, no behavior change |
| `perf` | Performance improvement |
| `style` | Formatting, whitespace only |
| `docs` | Documentation only |
| `test` | Adding or updating tests |
| `chore` | Build, tooling, dependencies, config |
| `ci` | CI/CD pipeline changes |
| `security` | Security hardening or vulnerability fix |
| `revert` | Reverting a previous commit |

### Scope Rules

- Derive from primary directory or module: `db`, `api`, `ui`, `auth`, `pipeline`, `rag`, `embed`
- Lowercase, single word when possible
- Omit scope if changes span 3+ unrelated modules
- Match scopes from recent `git log` output when applicable

### Subject Line Rules (always English)

- Imperative mood: "add", "fix", "update" — NOT "added", "fixes", "updates"
- Lowercase first letter after colon
- Max 72 characters total
- No trailing period
- Be specific: "add retry logic for failed API calls" not "update API code"

### Body Rules

Include body when changes touch 2+ files or diff exceeds 30 lines.

- Blank line after subject
- Wrap at 72 characters
- Summarize: what changed, why, key details
- Use bullet points for distinct changes
- Write body in user's chosen language (EN or VI)

**EN example:**
```
feat(pipeline): add citation extraction for Vietnamese EHR records

- Parse structured SOAP sections from clinical note text
- Map extracted entities to ICD-10-VM and SNOMED-CT codes
- Store citation spans with source document references in PostgreSQL
```

**VI example:**
```
feat(pipeline): add citation extraction for Vietnamese EHR records

- Phân tích các phần SOAP có cấu trúc từ văn bản ghi chú lâm sàng
- Ánh xạ thực thể trích xuất sang mã ICD-10-VM và SNOMED-CT
- Lưu trữ đoạn trích dẫn kèm tham chiếu tài liệu nguồn vào PostgreSQL
```

### Never Include

- Co-Authored-By lines
- AI/tool attribution ("Generated by", "Created with Claude")
- Emoji in commit messages
- Vague subjects ("update code", "fix stuff", "minor changes", "wip")

### Execute

```bash
git commit -m "$(cat <<'EOF'
type(scope): subject line

- Body point 1
- Body point 2
EOF
)"
```

Run `git status` after to confirm and display result.

## Batch Commit Mode

### Step 1: Inventory Changes

```bash
git status --porcelain
```

Parse each line: status code + file path.

### Step 2: Group by Logical Affinity

Group files in this priority order:

1. **Co-dependent pairs**: implementation + test, component + styles/types
2. **Manifest + lock pairs**: `package.json` + `package-lock.json`, `pyproject.toml` + `uv.lock`
3. **Same feature/module directory**: all files under `src/pipeline/`, `src/rag/`, etc.
4. **Same change type**: all config files, all docs, all migrations
5. **Catch-all**: remaining unrelated files

Target: **2–5 commits**. Never exceed 7. If only 1 group results, fall back to single mode.

### Step 3: Present Plan

Show the commit plan before executing:

```
Proposed commits:

1. feat(rag): add hybrid retrieval with BM25 and dense embeddings
   - src/rag/retriever.py
   - src/rag/bm25_index.py
   - tests/test_retriever.py

2. chore(deps): update dependencies
   - pyproject.toml
   - uv.lock

3. docs: update README with pipeline architecture diagram
   - README.md
```

Ask: **"Proceed with these commits?"** — wait for confirmation before executing.

### Step 4: Execute Sequentially

For each group:

1. Reset staging: `git reset` (if previous staging exists)
2. Stage files: `git add <file1> <file2> ...`
3. Generate commit message (same rules as single mode)
4. Execute: `git commit -m "..."`
5. Verify: check exit code before continuing

**If any commit fails** (pre-commit hook, lint error, etc.): stop immediately, report error, do NOT continue. Never use `--no-verify` unless user explicitly requests it.

### Step 5: Summary

```
✓ Created 3 commits:
  a1b2c3d feat(rag): add hybrid retrieval with BM25 and dense embeddings
  e4f5g6h chore(deps): update dependencies
  i7j8k9l docs: update README with pipeline architecture diagram
```

## Edge Cases

| Scenario | Handling |
|----------|----------|
| Binary files | Include in commit, note as "add/update binary assets", skip content analysis |
| Lock files | Always group with their manifest, never standalone |
| Very large diffs (>1000 lines/file) | Use `--stat` + read first 100 lines for context |
| Untracked files only | Stage and commit normally, typically `feat` or `chore` |
| Submodule changes | Note in message, do not analyze submodule internals |
| Pre-commit hook failure | Report clearly, do NOT retry with `--no-verify` |
| Empty staging after auto-detect | Switch to batch mode, inform user |
| `.env` or secrets files | Warn user: "This file may contain secrets — are you sure you want to commit it?" |
